Exhibition System API

El lado servidor del Sistema de Exposiciones: una API REST en NestJS que valida, aplica reglas de negocio y persiste en PostgreSQL. Esta página (servida por el propio backend en la raíz) explica qué expone y cómo probarla, sin necesidad de tener el frontend corriendo.

Swagger (API) ↗ GET /api/v1/products → GET /api/v1/categories →

▣ Desplázate para recorrer el backend, de arriba hacia abajo.

Con qué está construido

Tres piezas del lado servidor, cada una con una sola responsabilidad. Todo vive en la carpeta backend/.

◆

API

NestJS 12

Recibe peticiones HTTP, valida los DTOs y despacha la lógica de negocio.

  • · Puerto 5555 con prefijo global /api/v1
  • · ValidationPipe global: whitelist + forbidNonWhitelisted
  • · CORS abierto (origin: '*')
  • · Módulos: categories, products y seeders
◆

Persistencia

TypeORM + PostgreSQL

Traduce los objetos del código a tablas y consultas SQL reales.

  • · Puerto 5432, base exhibition_system
  • · Schema autogenerado: synchronize: true (sin migraciones)
  • · autoLoadEntities: las entities se registran por módulo
  • · Relación Many-to-One: muchos productos por categoría

Qué expone la API

Todos los recursos viven bajo /api/v1. Prueba cualquier uno desde{" "} Swagger ↗.

products

  • GET /api/v1/products — listado
  • GET /api/v1/products/:id — detalle por id
  • POST /api/v1/products — crear (body validado)
  • PATCH /api/v1/products/:id — actualización parcial
  • DELETE /api/v1/products/:id — eliminar

categories

  • GET /api/v1/categories — listado
  • GET /api/v1/categories/:id — detalle por id
  • GET /api/v1/categories/slug/:slug — detalle por slug
  • POST /api/v1/categories — crear (body validado)
  • PATCH /api/v1/categories/:id — actualización parcial
  • DELETE /api/v1/categories/:id — eliminar

seeders

  • POST /api/v1/seeders — resetea y siembra 5 categorías × 5 productos (solo desarrollo)

El viaje de una petición (visto desde aquí)

Qué hace el backend cuando, por ejemplo, el frontend pide{" "} GET /api/v1/products:

  1. 1

    Llega al puerto 5555

    La petición HTTP entra al servidor; ServeStaticModule atiende la raíz / (esta página) y el resto pasa al prefijo /api/v1.

    backend/src/app.module.ts · main.ts
  2. 2

    Validación global

    El ValidationPipe valida el DTO con whitelist + forbidNonWhitelisted: un campo no declarado rechaza toda la request.

    backend/src/main.ts
  3. 3

    El controller despacha

    El controller del recurso (products o categories) recibe la ruta y delega en su service.

    backend/src/products/products.controller.ts
  4. 4

    TypeORM consulta PostgreSQL

    El service traduce la petición en una consulta TypeORM y PostgreSQL (puerto 5432) devuelve las filas.

    backend/src/products/products.service.ts
  5. 5

    La respuesta JSON regresa

    El JSON vuelve por /api/v1 y el frontend lo cachea con TanStack Query. Si no hay frontend, esta página y Swagger siguen siendo la puerta de entrada.

    GET /api/v1/products

Estructura del backend

Un módulo por dominio: controller (HTTP), service (lógica) y sus DTOs y entities. 

backend/
├── src/
│   ├── main.ts            # Bootstrap: prefijo /api/v1, ValidationPipe, Swagger, CORS
│   ├── app.module.ts      # TypeORM → PostgreSQL, config y ServeStaticModule
│   ├── categories/        # controller · service · dto · entities
│   ├── products/          # controller · service · dto · entities
│   └── seeders/           # POST /api/v1/seeders (5 categorías × 5 productos)
├── public/                # Esta landing, servida en la raíz del server
├── .env.template          # Plantilla: PORT=5555, API_PREFIX=/api/v1, datos de BD
└── package.json           # pnpm: dev · test · lint (oxlint) · format

backend/src/

El código TypeScript de la API. Sin migraciones: el schema se auto-genera al arrancar.

backend/public/

Archivos estáticos servidos en la raíz — esta página es el index.html que ves.
